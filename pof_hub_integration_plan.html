Scripts To Derive — Prioritized Build List

Tier 1: Wire Today Into Tomorrow (This Week)

P1 post_create_hook.py

Post-create hook for the File Drop API. When any file lands in the drop folder, this runs automatically: semantic scorer → chi hash → store results in shared memory. Connects semantic_scorer.py to routes_file_drop.py to /memory/store.

Input: file path → Output: chi hash + dominant vars + magnitude stored in memory

P1 job_manager.py

The durable job system from the architecture. Every action becomes a job with state transitions (queued → claimed → running → succeeded/failed). This is core/job_manager.py from the Build Order. Without it, nothing else in the 30-job-type registry can run.

Maps to: Build Order #4 — FastAPI app + jobs API

P1 scanner_to_jobs.py

Bridge script: takes folder scanner results and creates durable jobs for each fixable symptom. Scanner finds S03 (depth explosion, auto-fixable) → creates a folder_health_scan job → job goes to review queue if risky, or auto-executes if safe.

Maps to: Job Type "folder_health_scan" + Review Gate integration

P1 startup_health.py

Session-start healthcheck script. Checks: Hub API alive? Ollama alive? Qdrant alive? ntfy alive? Drop folder accessible? Postgres reachable? NLP API at 8700? Reports status to shared memory + ntfy. Run this first every session.

Replaces ad-hoc "is everything running?" checks

Tier 2: Intelligence Layer (Next Two Weeks)

P2 rename_worker.py

The rename suggestion engine from the Prompt Registry (P-REN-001). Takes a file + folder context + naming mode, calls Ollama locally, returns 3 candidate names with confidence scores. Never auto-applies — stages for review.

Maps to: Worker Matrix "rename_worker" + Prompt "prompts/rename_suggestion.md"

P2 classify_worker.py

File classification using the 4-layer stack (Physical → Semantic → Meta → Relational). Reads the file, runs the semantic scorer for Layer 2, applies the frozen meta enums for Layer 3, stores the result. This is where the 10D chi-variable space meets the job system.

Maps to: Worker Matrix "classify_worker" + Intelligence Lane "master_equation"

P2 duplicate_resolver.py

Beyond the scanner's C01 detection — this one decides what to DO about duplicates. Hashes match → compare dates, locations, folder context → recommend keeper → stage archive for the rest. Calls Ollama for semantic tiebreaks (P-DUP-001).

Maps to: Job Type "duplicate_resolve" + Prompt "prompts/duplicate_keeper.md"

P2 ollama_task_router.py

Central router for all 11 Ollama/NLP tasks in the Ollama_NLP_Tasks sheet. Each task has an ID (LLM-001 through LLM-011), a preferred lane (Ollama first vs OpenAI), and a prompt template. This script loads the right prompt, calls the right model, parses structured JSON output, and stores results.

Maps to: Ollama_NLP_Tasks sheet (all 11 tasks)

P2 folder_profile_engine.py

Loads the 15 folder profiles from the architecture and enforces their policies. Downloads folder gets Level 3/4 automation. Documents gets Level 2/3 review-first. Program roots get NEVER auto-touch. The policy engine from core/policy_engine.py.

Maps to: Folder Profiles sheet (15 profiles) + Build Order #5

Tier 3: Review & Safety (Week 3)

P3 review_gate.py

The 16 review gates from the architecture. Rename bulk > 20 files? Review. Delete anything? Review. Protected category detected? Block. Low confidence < 0.65? Escalate. This is the safety valve between intelligence and action.

Maps to: Review Gates sheet (16 gates)

P3 resource_gate.py

Pauses heavy workers when CPU > 55%, RAM > 80%, or battery low. Prevents the system from making the machine unusable during batch scans.

Maps to: Worker Matrix "resource_gate" + Build Order #7

P3 preference_learner.py

When you correct a rename or reclassification, this learns the pattern. Uses River/Markov for deterministic patterns, Ollama for ambiguous ones. Scoped per-folder so a Downloads preference doesn't leak into Documents.

Maps to: Intelligence Lane "preference_learner" + Prompt P-PREF-001

The Evaluation Framework

Every system needs to know if it's getting smarter or dumber. Here's how to score each layer:

Scanner Evaluation (Does it find real problems?)

P
Precision
Of the symptoms it flags, how many are real? Target: >90%. Test by scanning a known-clean folder — false positives should be near zero.
R
Recall
Of the real problems in a folder, how many does it catch? Test by seeding a folder with known symptoms (5 duplicates, 3 naming collisions, 1 config leak) and checking the scanner finds all of them.
G
Grade Accuracy
Does the A-F grade match human intuition? Have 3 people grade 10 folders blind, compare to scanner grade. Target: ±1 letter grade 90% of the time.
Δ
Delta Reliability
When comparing scan-to-scan, does the score change accurately reflect real improvement? Fix 5 symptoms → rescan → score should increase proportionally.

Classification Evaluation (Does the semantic scorer work?)

90%
Cross-AI Agreement (Already Validated)
18/20 documents agreed across Claude/GPT/Gemini on dominant χ-variables. This is the baseline. New files should maintain >85% agreement.
H
Hash Predictability
Give an LLM only the coordinate hash (e.g. GKC-3K5A-3F). Can it predict the document's domain and content family? Target: >80% accuracy on domain, >60% on content.
C
Completeness Coverage
982 axioms from 43 worldviews mapped to 10 variables — already passed. New test: scan 1000 files from diverse sources, check that no file gets all-zero scores (the system should find SOMETHING in everything).

Rename Evaluation (Are the suggestions good?)

A
Accept Rate
Of rename suggestions shown in the review queue, how many does David accept without editing? Target: >70% accept-as-is after 30 days of learning.
E
Edit Distance
When David edits a suggestion, how much does he change? Lower edit distance = better suggestion. Track Levenshtein distance over time.
S
Safety (No Breakage)
Zero tolerance: no rename suggestion should ever break an import, a link, or a program dependency. Test by scanning program roots — the system should refuse to suggest renames for anything in I01 zones.

Overall System Evaluation

⬆
Folder Health Over Time
Run the scanner on the same 10 folders monthly. Plot scores. The system is working if scores trend upward. If they plateau or drop, the intelligence layer isn't translating into action.
⚡
Time to First Useful Action
From cold start, how long until the system produces something you actually use? Today: ~5 minutes (run scanner, read report). Target after full build: <30 seconds (watcher detects file, classifies, suggests action, you approve).

How To Make It More Intelligent

Level 1: Deterministic Intelligence (No AI needed)

This is where 80% of the value comes from with 20% of the complexity:

• Extension priors — a .lean file is always code, a .pdf in a folder called "invoices" is always financial. No LLM needed.

• Path heuristics — fis/nlp/path_heuristics.py already does this. Wire it in.

• Folder role propagation — if a folder is classified as "research," every new file inherits a research bias until proven otherwise.

• Temporal patterns — files created at 2 AM are probably work sessions. Files created in bulk on one day are probably imports. No AI needed to detect these.

• Co-occurrence — files that always appear together (.py + .pyc, .tex + .pdf) should be linked automatically.

Level 2: Local AI Intelligence (Ollama, zero cost)

Your llama3.2:3b is already running. Use it for:

• Rename suggestions — small context packet (filename + folder + excerpt), structured JSON output. P-REN-001.

• Tag inference — when deterministic classification is low-confidence. P-TAG-001.

• Folder summaries — "this folder contains 47 files, mostly PDFs about thermodynamics." P-FOLD-001.

• Duplicate tiebreak — when hashes match but folder context differs, which is the "keeper"? P-DUP-001.

• Review explanations — "this rename was blocked because the folder contains a package.json." P-REVIEW-001.

Level 3: Cross-Session Intelligence (Memory API)

The shared memory we built today enables something new — learning across time:

• Preference accumulation — every rename David accepts/rejects is a training signal. Store it. After 50 signals, the rename engine should predict David's naming preferences with >70% accuracy.

• Pattern extraction — "David always renames AI exports to include the date and source AI." Extract this rule from the history, propose it as a permanent rule.

• Cross-AI synthesis — Claude classifies a file one way, Ollama classifies it another way. Store both. Over time, learn which AI is more accurate for which file types.

• Temporal correlation — "Lean builds always happen after Kimi sessions." "Website deploys always follow writing sessions." These patterns emerge from the memory log.

Level 4: The Master Equation Applied Reflexively

The semantic scorer uses the χ-variables to classify documents. But the system itself can be scored on the same variables:

• G (Grace) — does the system extend patience to ambiguous files instead of force-classifying them?

• M (Moral Alignment) — does it protect private/sensitive files consistently?

• E (Epistemic Integrity) — does it admit uncertainty? (confidence scores, review gates)

• S (Structural Order) — is the folder tree getting cleaner over time?

• T (Temporal Faithfulness) — does it maintain consistency across sessions?

• K (Community/Koinonia) — do the AIs actually communicate well through shared memory?

• R (Repentance/Error Correction) — when it makes a bad classification, does the correction propagate?

• Q (Qualia/Consciousness) — does the system know what it doesn't know?

• F (Faith/Trust) — do you trust it enough to increase automation levels over time?

• C (Christological Center) — is there a single source of truth? (the hub DB, not scattered scripts)

The system's own χ-score is the ultimate evaluation metric.

The Process — How This Should Run Day to Day

1
Session Start: startup_health.py

Checks all services, reports to memory + ntfy. You know before you type a word whether everything is alive.

2
Background: File watchers running

Downloads, Desktop, AI_Outbox watched. New file → intake job → hash → classify → store. You don't touch this.

3
Periodic: Folder health scan

Scanner runs on key folders nightly. Score trends stored in memory. ntfy alerts only on regressions.

4
On Demand: Review queue

Risky actions accumulate. You open the frontend, see 12 rename suggestions and 3 archive proposals, approve/reject in bulk. 30 seconds.

5
Cross-AI: File Drop + Memory

Kimi stores a Lean result → Memory API. Ollama analyzes a document → File Drop. Claude reads both next session. The shared memory is the connective tissue.

6
Monthly: Evaluation pass

Run the full eval framework. Plot folder health trends. Check rename accept rates. Measure cross-AI agreement. Adjust automation levels based on data.
